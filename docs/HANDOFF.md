## 1. 背景与协作方式

## 2. 技术栈决定

| 部分 | 决定 | 状态 |
|---|---|---|
| 游戏客户端 | Cocos Creator **2.4.14** + TypeScript | 已确定 |
| 发布平台 | **Web + 微信小游戏**，两者都要 | 已确定 |
| 登录方式 | 账号 + 密码 | 已确定 |
| 后端 | 倾向 **NestJS**（最接近 Spring Boot）+ TypeORM + MySQL + JWT + Swagger | **暂缓**，先做游戏，后端之后再定 |

### 为什么后端暂缓

- 游戏本体才是毕设核心。存档和排行榜的数据结构取决于玩法，现在设计后端容易返工。
- 客户端要预留**数据服务接口**，以后接后端时不用改游戏逻辑：

```
IDataService（登录、读存档、写存档、提交成绩、拉排行榜）
├── LocalDataService   # 当前：localStorage + 假排行榜数据
└── RemoteDataService  # 以后：调用后端 HTTP 接口
```

### 之前讨论过的后端方案（供以后参考）

- 目录结构：仓库根目录下分 `client/`（Cocos）、`server/`（NestJS）、`admin/`（管理后台，后期再做）、`docs/`。不用 monorepo 工具，各项目独立安装依赖。
- NestJS 模块：`auth`、`user`、`save`（存档）、`rank`（排行榜），以及 `common`（统一响应拦截器、全局异常过滤器、业务错误码、全局 JWT 守卫 + `@Public()`、`@CurrentUser()`）。
- 统一响应格式为 `{ code, data, msg }`，只用 access token（有效期 7 天），不做 refresh token。开发阶段用 TypeORM `synchronize`，部署前改为 migration。
- 数据表设想：`user`；`player_save`（和用户一对一，常用字段单独建列，扩展数据放 JSON 列）；`score_record`（每次通关一条记录，排行榜取每个用户的最好成绩，服务端校验分数是否合理）。
- 客户端网络层用 `XMLHttpRequest` 封装，因为微信小游戏也支持它；token 存在 `cc.sys.localStorage`；收到 401 时派发事件，由 UI 决定跳转。
- 后端需要打开 CORS，因为 Cocos 浏览器预览运行在 `localhost:7456`。微信小游戏要求 HTTPS 和域名白名单。
- NestJS 11 要求 Node 20 及以上。本机目前是 **Node 14.21.3**，到时需要用 **nvm** 安装新版本，同时保留 14。

## 3. 游戏设计（已确定的方向）

### 核心机制：水的三态切换

主角是一滴水精灵，可以在三种形态之间切换，每种形态的物理特性和能力都不同：

| 形态 | 手感 | 能力 | 弱点 |
|---|---|---|---|
| 水 | 普通跑跳，比较灵活 | 穿过栅栏缝隙、浇灭火焰 | 大火会把它蒸发 |
| 冰 | 重，跳得低，在地面上打滑 | 压下压力板、对尖刺免疫、撞碎脆墙 | 遇火融化 |
| 蒸汽 | 缓慢上浮，不能站在地上，**只能维持 3 秒** | 被风口吹着飞、飘到高处 | 遇到冷气凝结成水；会被风灵吹走 |

### 缝合的次要机制

1. **冰雕残影**（必做，第 1 章引入）：长按切换键，在原地留下一座冰雕，本体变回水。冰雕可以一直压着压力板，也可以当垫脚平台。同一时间最多一座。
2. **水之剧院 / 舞台光影**（第 2 章引入）：聚光灯会发热，水进入灯光会被强制蒸发，冰会慢慢融化。
3. **轻量战斗 + Boss**（可选，时间够再做）：不设单独的攻击键，敌人与形态之间有相克关系。

### 操作

- 移动、跳跃、切换形态、**形态技能**。手机端是摇杆加三个按钮。
- 形态技能：水 = 水弹（远程灭火、打开关）；冰 = 下砸（空中急坠，砸怪、砸脆地板）；蒸汽 = 凝雨（浇灭下方的火，自己缓慢下降）。
- **血量等于水量**，满血 3 格。受伤时角色变小，吃水滴恢复。

### 敌人设计（组件化：行为组件 + 属性标签 + 相克规则表）

- 行为组件：巡逻、飞行盘旋、追踪、定点射击、潜伏突袭。
- 属性和敌人候选（最终做 8 到 10 种即可）：
  - 火系：火苗史莱姆、余烬蝙蝠、喷火炮台
  - 寒系：霜冻甲虫（会把水冻成冰）、寒气水母
  - 风系：风灵（吹走蒸汽，冰不受影响）
  - 吸水系：海绵怪（吸走水量）、沙虫
  - 雷系：电鳗（水导电、冰绝缘）、雷云（可以引到水池上电死其他怪）
  - 剧院系（第 2 章）：提线木偶（灯光下才会动）、幕布幽灵（灯灭时出现）、镜像演员
- Boss：第 1 章巨型海绵王；第 2 章傀儡师；第 3 章熔炉之心（三阶段，分别对应三种形态）。
- 相克规则用配置表描述，例如"水 + 火 = 怪死"、"冰 + 火 = 玩家受伤"。论文可以写一节"组件化与数据驱动的敌人系统"。

### 章节结构（每章引入一个新机制）

- 第 0 章：教学，学会三种形态
- 第 1 章：冰雕残影
- 第 2 章：水之剧院与灯光机关
- 第 3 章：敌人、Boss，综合运用所有机制
- 总共 8 到 10 关，每关 1 到 3 分钟。评分包括通关时间和 3 颗隐藏水晶，给出 1 到 3 星，排行榜按最快通关时间排名。

### 后续再定（开发者明确表示可以后做）

美术风格、世界观和剧情、成长系统、成就、关卡编辑器、每日挑战。

### 关键实现约定

- **玩家移动**：刚体 `gravityScale = 0`，速度每帧由代码计算后写入 `linearVelocity`，Box2D 只负责碰撞。已实现土狼时间、跳跃缓冲、松开跳跃键小跳。
- **地面检测**：从脚底两个角向下发射射线，忽略传感器和当前形态可穿过的物体。
- **可穿过的实体**：在玩家的 `onPreSolve` 里对 `PassThrough` 设置 `contact.disabledOnce = true`。切换形态前用 `testAABB` 检查，如果新形态会卡在实体里就拒绝切换，并播放抖动反馈。
- **机关与玩家解耦**：机关只依赖 `IPlayer` 接口。玩家在 `onBeginContact/onEndContact` 中调用对方节点上实现了 `IPlayerTrigger` 的组件。区域效果由玩家在 `update` 里根据 `zoneCounts` 和当前形态结算，不在物理回调里改状态。
- **不缩放带物理的节点**：动画只作用在子节点 `Visual` 上，避免碰撞体重建。
- **地图坐标**：地图第 0 行是最上面一行，关卡左下角位于世界层原点；世界层放在 Canvas 原点。墙格子会贪心合并成大矩形，避免角色在接缝处被卡住。
- **HUD** 挂在相机节点下，随镜头移动。
- 原型阶段规则：任意压力板压下后打开所有门，且保持打开（`latch = true`）。

`#` 墙，`|` 栅栏（只有水能过），`x` 尖刺（只有冰免疫），`P` 压力板（只有冰能压下），`D` 门，`^` 风口，`~` 冷气，`S` 出生点，`G` 终点，`.` 空地。
